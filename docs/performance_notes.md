# 性能の調査メモ(解析処理)

## 計測方法

実データのリプレイ(2025-12-08 青森県東方沖M7.5、398フレーム、観測点1784点)を、`tools/replay-eval.mts` で流す。
プロファイルは、tsx(`keepNames`などの変換が入り、約2倍遅くなる)を使わず、esbuildでバンドルしたJSを
`node --cpu-prof` で取る。

```
node -e "require('esbuild').buildSync({entryPoints:['tools/replay-eval.mts'],bundle:true,outfile:'/tmp/replay.mjs',
  format:'esm',platform:'node',external:['node:*'],define:{'import.meta.url':'\"file:///x\"'}})"
node --cpu-prof --cpu-prof-dir=/tmp/prof /tmp/replay.mjs --replay <.bin> --stations <.json> --truth "..."
```

## 結果(レポート7.3「観測点間距離の最適化」の検証)

レポートは「初期化の観測点間距離が総当たり(O(N²))」を問題にしていたが、実データのプロファイルでは、
**時間の大半は別の場所**だった(1tickあたりの停止時間の大部分は震源推定):

| 場所 | 最適化前の自己時間 | 内容 |
|---|---|---|
| `calcPeakIntensity`(想定震度) | 54% | 候補の震源×マグニチュード候補×観測点で、約千回/候補 |
| `lookupJmaTravelTime`(走時表の参照) | 14〜19% | 呼び出しごとに配列・クロージャ・結果オブジェクトを生成。P波もS波も計算 |
| 観測点間の距離(haversine) | 5〜7% | |
| `initialize`の近傍探索(O(N²)) | 起動時の1回のみ(約125ms) | 観測点が変わるたびに1回 |

## 行った最適化

出力が1ビットも変わらないもの(実リプレイ398tickの全フィールドの一致で確認):

1. 走時表の参照: P波だけを引く `lookupJmaPTimeSec`(割り当てなし)。二分探索の結果は配列でなく変数で返す。
   目盛りが狭義単調増加の表では、位置の索引(ヒント表)から1〜2歩で区間を見つける(単調でなければ二分探索)。
2. 想定震度: マグニチュードと深さだけで決まる項を、観測点のループの外へ(`createPeakIntensityModel`)。
3. 近傍探索: 格子の空間インデックス(`spatialIndex.ts`)で候補を絞る。近傍リストの順序まで、総当たりと同じ。
4. 広域パス(`globalTimeSearch`)・独立震源判定(`independentSourceFit`): 震央距離は深さに依らないので、
   (緯度, 経度)ごとに1回だけ計算して、深さを変えた評価で使い回す。下位25%点の取得は、比較関数つきの
   `Array.sort` から数値型配列の昇順ソートへ(NaNが混じる時だけ従来のソート)。
5. 候補震源の評価(`computeErrorLevel`等): 候補位置から各検知点への距離を、直近1件のキャッシュで共有する
   (到達時刻・発生時刻・震度の整合性・S-P時間差の複数の関数が、同じ距離を使う)。推定の入口で破棄する。

結果が最後の桁だけ変わるもの(許容誤差内で一致。実リプレイでは、推定結果の全フィールドが完全一致した):

6. 想定震度の式: べき乗と対数の往復(`log10(10^x × 1.31)`)を、等価な式 `x + log10(1.31)` に置き換える。
   超越関数が1回あたり3回から1回に減り、約3.7倍速い。旧実装との差は最大 8.9e-16 震度
   (`tests/hotpathEquivalence.test.ts`で、2万通りの入力に対し許容誤差1e-12以内を確認)。

## 効果(実リプレイ398フレーム、解析処理の合計。同じ環境での計測。ばらつきは約±10%)

| 段階 | 合計時間 | 1tickの最大停止時間 |
|---|---|---|
| 最適化前 | 89.1秒 | 897ms |
| 1〜3 | 54.4秒 | 667ms |
| 6を追加 | 32.6秒 | 652ms |
| 4を追加 | 28.0秒 | 420ms |
| 5を追加 | 23.7秒 | 388ms |
| 1のヒント表を追加(最終) | **19.1秒(約79%短縮)** | **281ms** |

`initialize`の近傍探索は約125ms → 約10ms(起動時・観測点の更新時に1回)。

最適化前後の出力(推定結果の全フィールド・検知点数・イベント数)は、全398tickで完全に一致した
(`tests/hotpathEquivalence.test.ts`、`tests/spatialIndex.test.ts`、リプレイ全体の比較)。

## 残っている時間と、未適用の案

最適化後の主な内訳(自己時間): 震源推定の時間探索(`robustTimeCost`)・震度の整合性(`fitMagnitude`)・
距離(`haversineKm`)・走時表の補間・想定震度の式(`log10` 1回)。いずれも1つが1割台で、突出した箇所は無い。
さらに縮めるなら、次はアルゴリズム側(結果が変わりうる):

- 広域パス(`estimateGlobalPass`)は、検知点が増えるたびに、全探索(粗い格子289×9深さ+細かい格子)を最初からやり直す。
  前回の解の近傍だけを探す・数秒おきにしか行わない、などで、さらに減らせる。ただし推定結果とその時刻が変わる。
- 推定自体をWebWorkerで行う(`?analysisWorker=1`)と、メインスレッドの停止はほぼ無くなる。
